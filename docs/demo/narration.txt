GridPulse is a smart meter telemetry platform built by Team 14. A power distribution utility receives readings from five thousand meters on twenty feeders in six zones: ninety-six readings per meter per day, almost half a million events daily. The data arrives late, duplicated, in two schema versions and in mixed units. Bills get disputed, and tampering or outages are found only after customers complain. GridPulse fixes that with one daily, fully automated pipeline.

Gateways drop JSON files into a landing zone. An extractor loads every line, unchanged, into a bronze Parquet lake partitioned by arrival date and zone. dbt on DuckDB then normalises everything: energy to kilowatt hours, timestamps to Indian Standard Time, duplicates removed, readings ordered, and every fifteen-minute slot placed on a grid where missing slots are marked as gaps, never invented. From the cumulative register we compute interval consumption, handling meter rollovers. Great Expectations gates block bad data. Clean marts are published to Postgres, and Superset reads them through a read-only user. Airflow runs it all, everything in Docker with one command.

This is Airflow. The daily pipeline runs at one thirty in the morning, Indian time. It reloads a three-day window so late files are absorbed automatically, builds and tests the dbt models, runs the quality gates, publishes to Postgres, records pipeline metrics and alerts, and applies thirty-day retention. Every task retries twice. If a task still fails, a callback writes a critical alert. A separate backfill pipeline reprocesses any date range. The seven-day backfill you see here completed in under four minutes.

Here is the network operations dashboard. The first tab shows consumption per feeder, by day and by hour, and per zone. You can see the evening peak clearly. Every number here reconciles exactly: hourly totals equal the register deltas recomputed from staging, and feeder, zone and billing totals all match, to four decimal places.

The anomalies tab is for revenue protection. Three detectors run every day. Spike: an interval far above the meter's own thirty-day history. We measured the textbook z-score rule first. It flagged almost every meter, so we added a size guard, recorded in an architecture decision. Tamper: a meter flat at zero for two days while its feeder neighbours keep consuming. Outage: thirty percent or more of a feeder's meters going silent at the same time. Against our synthetic ground truth we catch five of five spikes, three of three tampers and the outage, with zero false positives, and the twenty percent control feeder correctly stays silent.

Completeness per zone shows the share of expected readings received each day. A meter day below ninety percent is flagged as low completeness and excluded from confident billing. Here you can see the outage day dip in zone four.

Pipeline health is for the on-call engineer. Each run records rows ingested, rejected rows, duplicate rate, completeness and ingest lag. Alerts appear below. These two late-data alerts fired because a gateway file arrived five days late, outside the three-day window, and the runbook tells you to run a backfill. Task failures land here too, as critical alerts.

Everything is delivered as code and documents: ideation, requirements and traceability, architecture with six decision records, the low-level design, a test plan, and test results with fourteen logged and closed defects. Seventy-two automated tests give ninety-five percent coverage. The runbook includes backfill, rollback and failure drills that we actually executed. One command, make demo, takes a fresh machine to this dashboard in about eleven minutes.

GridPulse: trustworthy billing numbers, early warning of tampering and outages, and a pipeline that runs itself. Thank you.
